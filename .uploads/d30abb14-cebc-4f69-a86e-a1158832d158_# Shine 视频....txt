## 三、项目目标

Shine 的最终目标是让普通 Windows 用户安装项目后，可以通过简单的 Web 引导完成本机制作环境的准备，使用 MiniMax-H3 生成 AI 短剧。

目前部分用户从 GitHub 拉取 main 后，可以进入 Web 工作台，但无法完成真实制作初始化。

核心问题是：

**系统能够检测缺失的软件、硬件和环境条件，却不能把可自动修复的问题交给已有安装能力处理，反而在检测阶段直接终止。**

本次目标是实现：

> 自动检测 → 分类诊断 → 安全复用 → 生成修复计划 → 用户统一确认 → 自动下载与安装 → 哈希校验 → 自动复查 → 模型适配 → ComfyUI 配置 → 工作流验证 → 启用对应制作能力。

一切必须基于真实环境事实。

严禁通过绕过检查、虚构资源状态、硬编码成功结果来实现表面上的初始化通过。

## 六、P1-A：基础工具自动补装闭环

现有 `bootstrap.ps1` 已经具备工具下载能力，但 Web 初始化与该能力没有形成完整闭环。

请实现以下目标。

### 6.1 精确检测

环境检测必须输出：

- 工具名称
- 当前版本
- 目标最低版本
- 是否已安装
- 是否达标
- 是否可以自动修复
- 下载包身份
- 是否需要重新识别当前进程环境

对于本次样本：

FFmpeg 和 FFprobe 应识别为同一固定工具包的两个命令。

PowerShell 7 应识别为第二个缺失工具包。

Node、npm、uv 已达标，不允许重复安装。

### 6.2 自动修复计划

引入清晰的环境修复计划合同，优先复用已有安装计划能力。

计划必须具备稳定 ID、内容摘要、目标根目录、待修复工具、固定版本、来源、预计下载大小、操作授权状态、执行状态和结果证据。

不得让环境检测 GET 接口产生下载、安装、改 PATH 或启动进程等副作用。

只读检测与真实执行必须分离。

### 6.3 Windows PowerShell 自举

当前 Web 提示通过 `pwsh` 运行 `bootstrap.ps1`，但缺失项恰好包含 PowerShell 7。

必须修复这个循环依赖。

基础自举使用 Windows 自带 PowerShell 5.1 支持的执行路径，例如 `powershell.exe`。

不能要求用户先手动安装 PowerShell 7 才能执行补装。

不得通过 Web 传入任意 Shell 命令。

### 6.4 执行安全

新增执行通道必须满足：

- 本机操作员授权。
- 固定工具及参数白名单。
- 不允许任意命令执行。
- 不允许远程客户端触发本机安装。
- 参数数组调用，禁止字符串拼接执行 Shell。
- 安装根目录路径校验。
- 禁止路径穿越与非预期覆盖。
- 不提升系统管理员权限。
- 不自动安装或升级 NVIDIA 驱动。
- 不修改与 Shine 无关的系统配置。
- 不向日志写入 API Key、密码、令牌。

复用已有操作员身份、审批、日志和持久化执行能力。

如果现有执行器不能承载工具补装，请增加最小兼容扩展，但不能绕开既有安全架构。

### 6.5 安装完成自动恢复

Windows PATH 更新可能无法被运行中的 API 进程立即读取。

必须解决安装完成但检测仍报缺失的问题。

优先使用受管工具实际路径和可验证的工具注册信息。

必要时通过已有安全生命周期管理刷新服务，而不是直接要求用户重启整台电脑。

执行成功后自动重新检查工具版本。

只有工具真实可执行且达到版本要求才能标记成功。

重复点击、刷新网页或后端重启不得重复安装同一工具包。

## 七、P1-B：环境阻断分级与准入解耦

当前环境报告将所有 blockers 混合返回，导致任何一种阻断都让整条初始化链停止。

请改造为明确分级。

建议使用以下语义，名称可与既有架构调整保持一致：

```text
AUTO_REPAIRABLE
USER_ACTION_REQUIRED
HARDWARE_INCOMPATIBLE
DETECTION_UNKNOWN
ALREADY_AVAILABLE
```

同时区分作用范围：

```text
BOOTSTRAP
RESOURCE_PREPARATION
VARIANT_QUALIFICATION
SERVICE_CONFIGURATION
PRODUCTION_ACTIVATION
```

不得简单将全部 blockers 删除。

举例：

FFmpeg 缺失可以阻断依赖 FFmpeg 的工作，但不能阻断模型候选查询和工具补装计划创建。

默认 INT8 显存不够，可以阻断 INT8 正式生产，但不应阻断其他 H3 候选变体的受控资源准备。

8188 被其他进程占用，可以阻断对该端口的错误绑定，但不应阻断选择其他合法端口。

必须为每种问题返回准确的原因、实际值、要求值及下一步动作。

前后端使用一致的机器可读状态，不允许依赖中文错误文字反向推断问题类型。

## 八、P1-C：RTX 4070 与 H3 模型分档

本轮不开发新的 H3 量化模型。

必须复用仓库已有变体清单，包括：

- `h3-ref2va-int8-convrot`
- `ref2va-lowend-candidate`
- `ref2va-nvfp4-lowend`

以及最新 main 已经合入的其他合法变体。

### 8.1 分档准入

不能使用默认 INT8 模型要求对所有 H3 模型进行统一阻断。

要求用户所选变体决定：

1. 部署清单。
2. 所需组件。
3. 硬件要求。
4. 可复用资源。
5. 是否允许下载。
6. 是否具备生产验收证据。
7. 对应工作流。
8. 最终是否允许真实生成。

如用户未选择变体，应先显示可选方案及其状态，不能暗中选择明显不适配的默认模型并开始几十 GB 下载。

### 8.2 候选方案

现有 W6A8 和 NVFP4 的验收状态必须保持真实。

`CANDIDATE` 不等于 `SUPPORTED`。

对于固定来源、哈希明确、允许受控准备的候选方案，用户明确确认后可以进入资源下载和校验阶段。

但是下载完成仅证明资源已整备。

不能自动声明：

- 模型生产兼容。
- CUDA 节点运行成功。
- 显存满足完整推理。
- 工作流完成真机验收。

必须区分：

```text
RESOURCE_PREPARED
FILES_VERIFIED
WORKFLOW_REGISTERED
RUNTIME_CONTRACT_VERIFIED
TRIAL_READY
PRODUCTION_READY
```

复用现有 readiness 和统一调度层，不得发明第二套互相矛盾的状态。

### 8.3 工作流继承

Web 向导、专业设置、安装计划和最终激活必须使用同一个用户选定的模型变体。

不允许在前端选择 W6A8，进入真实制作向导后又隐式下载默认 INT8。

不允许跨变体错误混用 checkpoint、VAE、LoRA 或不兼容工作流。

## 九、P1-D：32GB 级内存检测修复

当前样本检测到 31525 MiB 物理内存。

默认 INT8 模型清单要求 32768 MiB，而 `effective_floor_mb()` 存在固定 1024 MiB 容差。

请审查这套计算是否与 Windows 实际报告方式、硬件保留内存和模型准入逻辑一致。

必须区分：

- 物理安装内存容量。
- 操作系统报告的物理总量。
- 当前可用内存。
- Commit limit。
- 页面文件状态。
- 检测失败或取值未知。

对标称 32GB 内存但系统显示略低的情况，优先通过真实 Windows 系统信息进一步识别。

如果无法可靠确认，应报告 UNKNOWN 或需要复核，不得伪造已满足条件。

禁止通过无限扩大容差或统一降低最低内存要求来消除红色提示。

模型正式生产仍执行对应变体的实际资源准入。

请补充边界测试，包括：

- 31525 MiB。
- 31744 MiB。
- 32768 MiB。
- 真实 16GB 机器。
- 无法读取容量。
- 页面文件不足。
- 系统空闲内存不足。

预期结果必须根据明确的合同与证据定义，不允许为通过测试而改变数字。

## 十一、P1-F：Web 自动整备体验收束

面向普通用户，界面应做到：

用户点击一次「启用真实制作」，系统先完成所有只读检测，再展示一份简洁的整备计划。

推荐正常流程：

```text
检查电脑
    ↓
发现已有组件与缺失项
    ↓
推荐兼容模型方案
    ↓
确认自动整备
    ↓
下载及修复基础工具
    ↓
检查或下载 H3 模型
    ↓
配置 ComfyUI
    ↓
验证服务和工作流
    ↓
启用已达到验收条件的能力
```

界面主要展示：

- 已具备的能力。
- 需要补装的软件。
- 本机已有可复用资源。
- 预计新增下载量。
- 推荐或已选择的 H3 模型。
- 正在执行的步骤。
- 确实需要用户处理的问题。

允许展开高级详情查看原始代码、日志、哈希和计划信息。

不得再连续显示三个没有软件名称的“缺少必需的基础程序”。

不得让没有意义的“重新检查”形成无限循环。

### 11.1 统一授权

在现有授权机制允许的范围内，用户应尽量一次确认完整整备计划。

内部涉及多个受控执行步骤时，可以由既有授权能力按明确权限范围有序执行。

不得为了实现“一次点击”绕过计划审批、授权范围、哈希绑定或执行权限。

如既有安全合同要求分别确认不可合并的操作，应保留必要确认，但使用简洁明确的 UI。

### 11.2 持久恢复

浏览器关闭、刷新、网络超时、页面切换后必须能够重新附着已有任务。

执行状态以服务端记录为准。

已完成的下载不重新下载。

未知外部执行结果进入对账状态，不能自动重复执行。

用户取消确认后不得产生下载或安装副作用。

### 11.3 错误处理

错误信息必须包含：

- 失败的具体步骤。
- 失败原因。
- 是否可以重试。
- 是否保留已经下载的数据。
- 用户应如何继续。

禁止无期限转圈。

禁止将安装失败报告为成功。

## 十二、P1-G：架构一致性与数据安全

本轮应最小化改造范围，优先修复原有链路。

不得：

1. 新建独立于现有 ComfyOps 的模型下载器。
2. 新建独立的 ComfyUI 调度系统。
3. 重写完整 Launcher。

6. 改动用户作品、资产库、分镜书和生产结果。
7. 删除已有模型或用户缓存。
8. 擅自升级 GPU 驱动。
9. 擅自覆盖现有 Python、Node、ComfyUI 安装。
