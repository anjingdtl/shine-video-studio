# Shine 视频工作台：导演流程重构与全片持续生产建设方案

- 文档日期：2026-11-05（Asia/Shanghai）。
- 文档版本：1.0。
- 状态：依据本次讨论中用户已确认的产品方向编写，作为后续分阶段开发和验收的实施依据；本文新增设计尚未实现。
- 仓库基线：`main`，`baa6ea17598ae8264451318cf88726c3ccdad338`；基线版本为 0.2.0，不在本方案中擅自确定下一发行版本。
- 本轮交付：本 Markdown 建设方案；没有执行新机安装、模型下载、远程模型调用、真实生产、数据库迁移或代码改造。
- 核心目标：用户确认整部作品的创作与执行合同后，启动一次即可持续完成全片拍摄、逐集剪辑和交付，正常情况下不需要逐段值守。

## 1. 建设目标与范围

### 1.1 要解决的问题

现有导演模式已具备剧本分析、素材准备、风格冻结、专业 crew 链、H3 连续生产及成片装配基础。但这些能力尚未形成一条面向整部作品的完整旅程：

1. 剧本输入、长剧本大纲、素材准备分散在不同面板，用户需要跨页面寻找先后关系。
2. 页面步骤完成条件过粗，不能准确说明本次生产范围是否全部准备、生产和交付完成。
3. 局部分镜及一次生产批次的完成，尚不能代表全部剧本已生产完成。
4. 缺少统辖全部分集、生产批次、局部阻塞和交付的持久化全片生产计划。
5. 新机准备已有硬件检测和固定部署目录，尚需形成按机器能力推荐完整模型组合、安装后实测反馈的闭环。
6. 短样本出片证据无法证明数小时至数十小时的持续生产可靠性。

### 1.2 用户已确认的产品决定

| 编号 | 决定 | 本方案的执行含义 |
| --- | --- | --- |
| D01 | 双入口 | 输入想法生成剧本；导入现成剧本整理为可拍摄的统一范式，最终汇合到同一后续链路 |
| D02 | 结合 MiniMax-H3 能力编剧 | 前期考虑生成时长、对白可说完性、参考预算与连续性；最终提示词仍由唯一编译器输出 |
| D03 | 剧本统筹后提出素材需求点 | 每项需求允许使用已有素材、自行上传或项目生成候选，可混合选择 |
| D04 | 用户确认素材并最终冻结风格 | AI 不自动晋升主资产，不替用户冻结风格；素材生成前允许确认视觉方向草案 |
| D05 | 内嵌导演包 | 项目内选择某个导演包版本并启动，直接转交生产；正常使用不需要导出、导入 |
| D06 | 区分视频生成与成片交付 | 镜头产物、分集装配、全片交付、人工艺术验收分别记录 |
| D07 | 新机按能力推荐 | 检测机器和已有安装，分别推荐 H3 视频与生图的完整部署组合，用户确认后下载配置 |
| D08 | 整部作品无人值守生产 | 事先确认全部需求，持续完成所有选定集和镜头，允许生产运行数小时或数十小时 |
| D09 | 用户设置每集大致秒数 | 以叙事边界和对白完整性规划分集，支持合理浮动，不能强行裁断或凑时长 |
| D10 | 复用现有系统 | 一个数据库、一个任务编排体系、一个 H3 编译器、一套资源租约和审计；不引入第二个运行平台 |

### 1.3 首版范围

首版交付可从 Web 启动的“全片先规划、确认后持续生产”闭环：

- 全片剧本、分集、素材、风格和正式分镜在开拍前确认。
- 生成不可变导演包，绑定完整范围和生产政策。
- 后台持续推进全部生产批次，逐集装配和交付。
- 支持关闭浏览器、Worker 中断及机器重启后的核对和恢复。
- 独立部分继续生产，真实依赖链上的阻塞保留。
- 允许人工事后集中审阅，诚实保留待审结论。

后续增强包括：在用户另行授权的创作范围内逐步细化后续分镜、更复杂的转场和调色、多 GPU 及跨机器执行。首版不依赖这些增强。

### 1.4 不作出的承诺

- 无人值守不代表模型永不失败，也不代表所有作品自动获得艺术认可。
- 不以跳过技术错误、虚构素材或重放未知提交来换取“完成”。
- 首版不承诺任意硬件均可运行 H3，不承诺多卡显存自动相加，不自动切换云视频模型。
- 未完成真实长时测试前，不宣称已经验证数十小时可靠运行。

- 当前旅程存在 `approvedAssets.length > 0`、`shots.length > 0`、任一视频任务通过等粗粒度判断，应改为指定范围的完整性判断。

## 3. 总体产品旅程

### 3.1 六阶段主线

| 阶段 | 输入与用户动作 | Agent/系统职责 | 交付物与完成条件 |
| --- | --- | --- | --- |
| ① 创意与剧本 | 输入想法，或导入现成剧本；确认目标与限制 | 澄清、创作或整理，识别歧义和 H3 可拍摄性问题 | 已确认创作简报和可进入统筹的剧本版本 |
| ② 剧本统筹与素材 | 确认分集、人物/场景/道具需求，逐项选素材方式 | 形成剧本范式、分集方案、素材需求；生成候选并辅助一致性检查 | 剧本与分集确认，全部必要主素材确认，视觉方向确认，风格冻结 |
| ③ 镜头拆解 | 审阅逐场分镜、对白与声音安排 | 导演、摄影、场记、剪辑协作，检查工作流参考预算及连续性 | 全部选定范围的分镜、素材绑定和剪辑意图确认 |
| ④ 导演包 | 查看范围、缺项、预算与执行政策，确认版本 | 分析并冻结生产准入计划，编译检查，形成不可变包和机器就绪检查 | 创作已确认；启动前本机可执行检查通过 |
| ⑤ 视频生产 | 启动整部作品，查看进度或执行暂停 | 持久调度、受管 H3、技术检查、有限修复、跨批次推进 | 选定范围所有必要片段明确完成或列出阻塞；不能用一段通过代替全片完成 |
| ⑥ 后期成片 | 查看逐集预览、集中处理待审项、选择合集 | 剪辑、字幕、声音、受控调色、交付检查和归档 | 指定分集全部形成有效交付；艺术验收单独记录 |

第五、六阶段允许同时进行：前集已具备全部输入时开始装配，后集继续生成。阶段导航不应强制串行等待全部视频结束。

### 3.2 页面与交互原则

- “我的作品”作为项目入口和总览；六阶段用于作品内导航，“基础配置”不占制作阶段编号。
- 每阶段突出一个当前主动作、一个交付物摘要和必要的待决问题。
- 提示词、JSON、租约、哈希等工程细节放进可展开信息，界面保留可理解的原因与处理动作。
- 切换阶段、刷新、关闭页面后可从服务端恢复业务状态；组件保持挂载只能改善体验，不能承担持久化。
- 长列表分页、按集筛选和按需加载缩略图；不同时挂载数千个视频播放器，也不对每个片段单独高频轮询。
- 保留通用 `[hidden]` 隐藏规则、空值保护和用户手动展开状态。

### 3.3 阶段完成判断

所有完成判断绑定 `project_id + package_revision + scope_digest`：

- 素材完成：当前范围的所有必需需求均被有效正式素材满足；可选音色未提供不构成失败。
- 分镜完成：计划内每个来源范围有有效、已确认的分镜，既不遗漏也不重复覆盖。
- 导演包就绪：版本、授权、绑定及生产准入一致；本机检查另有有效期和配置指纹。
- 视频完成：所有必需片段均有当前有效产物且满足执行政策；没有尚未决定的必要片段。
- 分集完成：本集剪辑输入完整，装配产物通过技术与交付检查。
- 全片完成：包中全部必需集交付成功，可选合集按合同完成；待审列表和最终验收状态如实呈现。

## 4. 双入口与统一剧本范式

### 4.1 入口 A：输入想法

用户输入题材、人物、故事想法或一句话目标。Agent 自动整理已有信息，只询问会影响作品方向的必要缺项，形成可编辑 `CreativeBrief` 草案：

- 片型、受众、主题、核心冲突和结局方向。
- 语言、画幅、预计规模、每集目标秒数及容差。
- 用户锁定事实、禁止改动项、内容与预算限制。
- 视觉方向草案、现有素材约束和已知本机能力边界。

确认后生成大纲和剧本。用户通过对话或直接编辑提出修改；每次形成新版本，保留来源与差异。创作选择有歧义时先列问题，不能默默代替用户决定。

### 4.2 入口 B：导入现成剧本

先保存原文与内容哈希，按现有解析支持范围提取文字。扫描件、损坏文档或解析失败应明确提示，不自动把提取不完整的文字当成全文。

Agent 完成角色、场景、对白、时间线、关键道具及情节段落整理；所有事实可回到原文范围。输出应区分：

1. 原文明确事实。
2. 格式规范化结果。
3. 可拍摄性问题与改编建议。
4. 待用户确认的歧义。

允许自动整理格式。删改对白、改变人物关系、增加情节等语义变化必须展示差异并经用户确认。对白超出单次生成承载时优先拆镜；不擅自删词或加快到不可理解。

### 4.3 统一合同

新增合同名均为拟议名称，须在现有类型注册体系中实现和版本化：

| 合同 | 主要内容 |
| --- | --- |
| `CreativeBrief` | 创作目标、锁定项、语言、规模与输出意图 |
| `PreparedScript` | 场次、节拍、对白、人物实体、道具状态、来源范围 |
| `EpisodePlan` | 分集边界、覆盖范围、预计时长、容差、承接与结尾要求 |
| `StoryStateSnapshot` | 截至指定剧情位置的事实与状态，包含事实来源及有效版本 |

有界的单次调用通过现有 Gateway 和 `AgentTaskRecord` 执行。长文本采用原文块、分层大纲和针对当前段落的检索上下文；记录窗口来源、输入量与覆盖范围，不靠静默截断消除超限。

### 4.4 H3 规则介入的时点

- 剧本阶段检查可拍摄性：对白容量、角色数量、复杂动作、时长、参考预算和连续性。
- 正式分镜前必须登记并验证适用项目工作流，以真实节点和 `parameter_map` 约束参考设计。
- 新机尚未就绪时可以完成剧本草案；缺少真实能力的部分标为待验证，不能承诺正式分镜已可执行。
- H3 编译规则和项目冻结规则包保持版本/哈希固定；LLM 不输出可直接提交的自由格式最终提示词。

## 5. 剧本统筹、素材需求与风格冻结

### 5.1 素材需求点

沿用 `PreProductionPlan(purpose=asset_preparation)`、`AssetRequirement`、`MaterialRun` 及候选台账。每项需求至少展示：

- 稳定实体 ID、名称、类别及剧本首次出现顺序。
- 对应场次、分集和用途，必需或可选。
- 身份、服装、外观或环境的明确要求；未确定项单独列出。
- `reuse_master` / `upload` / `generate_candidate` 三种选择。
- 已选正式素材版本或候选，以及当前缺项和原因。

名称、标签和文件名可帮助用户阅读或建议匹配；角色身份连接仍以 `entity_id` 或明确资产 UUID 为权威。不同人物不得因同名或相似标签自动合并。

### 5.2 准备与确认顺序

1. 用户确认剧本和素材需求。
2. 用户确认素材视觉方向草案。
3. 逐项复用、上传或生成候选；不同需求可选不同方式。
4. 人物候选保持单人和清晰身份；场景候选不混入人物；关键道具候选突出单个目标，沿用现有经确认的构图合同。
5. 技术验证与语义评审分开；生成成功只表示候选可审阅。
6. 用户通过现有 action/snapshot 绑定的一次性授权明确晋升候选；上传主素材走现有确认使用流程。
7. 检查素材视觉方向与全片风格的一致性，用户确认并冻结 Style Bible。

候选生成和正式主资产是两种不同身份，AI 不能通过旧 approve/lock 接口绕过晋升。Fake、外部替身或离线证据不得转换为真实生产就绪。

### 5.3 风格和变更

- 素材生成前的视觉方向是草案；最终风格在用户审阅素材后冻结。
- 冻结风格、规则包、主素材版本在正式生产中不可原地改变。
- 后续发现必要缺项时，只补受影响需求并创建相关新版本，不抹除已有确认或产物。
- 改变冻结风格后重新计算分镜、生产准入及导演包影响；已拍历史保留。
- 远程文字模型授权和远程媒体字节授权分别处理；允许发送文字不等于允许上传图像/音频/视频。

## 6. 新机检测与部署组合推荐

### 6.1 目标与入口

首次运行通过现有 `一键安装并启动.cmd` / `SETUP.cmd` 进入基础配置；保留安装器幂等、非系统盘及默认至少 180 GiB 空间等现有分发要求。推荐新增方案若需更多空间，采用更高实际需求；不得因新推荐功能自动降低安装基线。

未完成模型准备仍可创建作品、写剧本、整理需求和上传素材；本地 H3 不可执行时禁止正式开拍。

### 6.2 检测内容

- 操作系统、CPU 架构、系统内存、目标盘可用空间、路径可写性。
- 每张 GPU 的 UUID、型号、显存总量/当前可用量、驱动和所选运行后端兼容性。
- 已安装 Python、PyTorch、ComfyUI、必要节点和 FFmpeg/FFprobe 的版本及导入能力。
- 用户指定或现有受控范围中的 ComfyUI 安装和模型文件；按已知哈希复用，避免重复下载。
- 当前运行任务、有效或待对账资源租约，以及外部服务是否占用端口。

检测默认不加载权重、不启动推理、不安装依赖；有界扫描不递归遍历全盘。NVIDIA 检测失败不能直接推断机器没有任何 GPU；未支持的 AMD/Intel/其他后端应诚实报告兼容性边界。多 GPU 首版选择明确的一张，不推断显存可合并。

### 6.3 推荐完整部署组合

在 `config/deployment/` 的固定目录与现有安装计划之上建立版本化兼容矩阵，按用途拆成：

1. H3 正式视频生成组合。
2. 生图候选准备组合；全部用户上传时允许不安装。
3. 可选审片或音色增强组合；不作为正常视频生产的默认阻塞项。

每个组合记录：模型身份/精度、配套编码器与 VAE、文件 revision/哈希/大小、工作流与节点版本、运行参数、资源要求、允许输出范围、许可来源和实测证据。

H3 是正式视频模型的固定产品选择。生图首个正式适配对象沿用 Qwen-Image-2.1；同模型的其他精度或组合先核对目录、工作流和许可证并实测后登记。不能仅因显存不足而静默切换其他生图模型，替代模型需单独纳入产品选择和兼容审计。

### 6.4 推荐算法与展示

推荐由可测试的规则执行，LLM 只解释理由，不临时编造下载地址、兼容性或阈值：

1. 过滤操作系统、架构、GPU 后端、驱动/运行库、许可与能力不兼容的组合。
2. 计算权重、编码器、VAE、激活、中间帧、解码、卸载和运行余量；下载大小不等于峰值显存。
3. 计算现有文件可复用量、下载量、安装临时空间、生产存储预留。
4. 按本机实测、相近硬件实测、估算的证据等级排序，再考虑质量偏好和时间代价。
5. 给出推荐、节省资源、更高质量选项；没有合法选项时列出具体阻塞。

不要在首版凭经验写死“某显存必定可跑”的通用表。现有固定硬件门槛需逐步迁移为方案约束，后端、安装器和前端共同读取，避免三套结论。

### 6.5 安装确认和实测

- 展示模型组合、来源、许可证条件、下载量、复用量、安装位置及验证任务。
- 一次显式确认可覆盖展示的固定下载和有序配置步骤；页面/项目/计划内容变化时停止沿用旧授权。
- 下载、哈希验证、运行库导入、工作流校验、真实生成验证分层记录。
- 若确认范围包含安装后小样，则安装完成后自动排队验证；否则提供明确的验证动作。不得把只读检测变成隐蔽推理。
- 生图验证覆盖人物、场景、道具三类；H3 验证覆盖实际模式及要求的参考能力。小尺寸成功不证明更大规格成功。
- 保存本机峰值显存/内存、耗时、输出规格、参考数量和成功/失败原因；估算在真实数据到来后更新。
- 样本只验证对应配置范围；不存在实测的范围保持待验证。配置、节点、驱动等关键指纹变化后使相关验证失效。

### 6.6 精度、质量和资源分开

权重精度属于部署方案；pdd8、原生步数和放大属于制作策略。更大的权重不自动意味着一定更好，更少采样也不自动等于更低运行峰值。

生图与 H3 默认分阶段独占 GPU，复用现有租约。生图结束后证明释放，才能推进视频；H3 series 运行中不得被生图或审片抢占。首版不要求两套主模型同时驻留。

## 7. 分集规划与长剧本覆盖

### 7.1 三种不同时间

| 时间 | 含义 | 处理原则 |
| --- | --- | --- |
| 单次 H3 时长 | 当前规则包和工作流允许的一次生成长度，现有基线为 4–15 秒、24 fps | 逐次校验，不是全片长度上限 |
| 每集目标时长 | 用户希望每集大约多少秒 | 根据叙事边界与对白完整性提出分集；显示容差 |
| 生产运行时长 | 实际电脑工作时间 | 按实测吞吐、返工、装配及等待估算，不与成片时长混写 |

### 7.2 分集参数

`EpisodePlan` 至少接受 `target_seconds`、显式 `tolerance_seconds`、结尾偏好、完整对白保护、选定剧情范围与可选集数目标。前端给合理默认值并展示；不静默产生硬性时长合同。

规划以场景/节拍为基础，将相邻剧情合并或拆分到适合的集边界，优先完整动作、对白和情绪节点。需检查：

- 每个必需来源范围恰好归属一次，不遗漏、不重复生产；片头、片尾、回顾等允许重复的内容必须显式声明。
- 同一对白不能因分集而无声丢失，结尾不从一句话中间截断。
- 目标过短或固定切点不可满足时，在开拍前展示原因和替代分法。
- 很短的最终剪辑可从合法长生成片段中取明确入出点，但不得声称生成器直接接受不支持的时长。
- 总集数与总时长在规划后给出估算，不承诺按字数精确推断真实表演时长。

### 7.3 层级和有界工作单元

采用“全文 → 分集 → 场次/生产段落 → 有界分镜工作单元 → 生成片段”的层级。保留现有单次合同上限，明确单位间映射；跨工作单元整合时使用服务端校验和全局稳定 ID。

局部三段分组只适用于对应切点表，不得把三段作为一集或全片的固定最大数量。整体分集时间使用整数时间基准，最终 EDL 使用实际媒体和帧边界校验，避免大量片段累加浮点误差。

### 7.4 计划事实与实际媒体承接

全片先规划需要已确认的剧情状态，并不要求先生成前一集的视频。正式生产时的媒体续接则必须等待前件真实通过：

- 计划阶段记录用户确认的剧情事实、人物状态和来源版本，状态明确为 `planned`。
- 实际产物产生后记录 `observed/verified` 的媒体证据，不把计划事实冒充已拍结果。
- 依赖末帧或音画上下文的后件，只能引用具体有效 job/attempt/artifact。
- 现有“上一段未生产则需人工承接事实”的路径应复用已确认剧本中的计划事实；两种事实类型分别建模，不能绕过真实媒体依赖。

## 8. 内嵌导演包

### 8.1 内容与身份

导演包是项目内不可变的执行输入快照，保存已有权威对象的 ID、版本和哈希，不另建可编辑素材库：

- 创作简报、原文及 PreparedScript、EpisodePlan 的版本。
- 全部选定集、场次、分镜/ShotSpec、已确认剪辑意图和素材需求覆盖表。
- 冻结 Style Bible、规则包及主资产版本/哈希。
- 逐镜参考绑定、工作流 profile/graph/parameter_map 身份、模型及能力指纹。
- 输出规格、对白语言、字幕与声音政策、质量与返工政策。
- 依赖图、预制作计划 ID/hash、启动授权和全片范围摘要。

包可采用根 manifest 加按集分页 manifest 的方式存入现有 Artifact Store，根 manifest 引用子 manifest 哈希。避免单个 SQLite JSON 字段承载整部长剧所有大文本或二进制媒体。

### 8.2 状态与操作

建议状态：`DRAFT → READY_FOR_CONFIRMATION → CONFIRMED`，并以单独的 `stale/revoked` 标记表达失效或撤销。一次成功生产不能使包获得永久本机就绪资格。

用户可查看版本差异、确认、选择启动范围和启动生产；导出仅作为可选备份增强，正常工作流直接内嵌转交。

包确认与运行启动分别留有审计：创作确认不是无限次数生产许可。重复 HTTP、双击和刷新必须返回相同启动结果；用户明确“再拍一版”才创建新运行。

若确认包同时应用专业角色提案，确认界面必须列出所应用的提案版本、分镜与绑定，沿用既有 apply 服务和权限检查；不能把“生成导演包”变成后台静默应用摄影/风格建议的权限入口。

### 8.3 运行时校验

启动时重新检查文件完整性、配置指纹、工作流能力、生产准入、运行资源及预算。Job 创建与 Worker 提交仍调用 `comfyops.preproduction.enforce`，导演包不能代替或禁用它。

派生末帧在包确认时尚不存在，包记录来源槽和派生规则。执行时绑定真实通过产物并保存 lineage，不把它晋升为主资产，也不篡改包的创作内容。

因此包确认前的编译检查分为静态可满足性检查和实际提交前的最终编译：缺少的动态末帧只能表示为显式依赖槽，不能虚构文件、hash 或完整渲染请求。依赖产物真实出现后，由同一个 H3PromptCompiler 完成最终 manifest 和请求，保存其 hash，再执行提交意图协议。

### 8.4 变更与最小重做范围

| 变更 | 影响与处理 |
| --- | --- |
| 字幕拼写、外挂/烧录方式、后期音量 | 更新交付合同与交付版本；未改变渲染输入时不重跑 H3 |
| 同一产物的剪辑入出点/顺序 | 更新 EDL 并重新校验剧情覆盖、时长与连续性；只重装配受影响交付 |
| 对白、人物身份、主素材、冻结风格 | 新建相关创作/素材/风格版本与包，重算受影响镜头及硬依赖；旧片保留 |
| 工作流、模型、画幅等渲染绑定 | 新包、新准入检查与相应真实能力验证，不能复用旧绑定的通过结论 |
| advisory 评审能力 revision | 按现有显式 rebind 和准入规则更新证据；不能因此默认重拍，也不能静默采用旧校准 |
| 增加集或缩小本次制作范围 | 确认新范围版本，生成新的运行或明确的续制作运行；不改写正在执行的旧范围 |

所有复用都验证输入身份、产物完整性和当前有效性。仅在用户看过影响清单并确认后推进需要新授权的变化。

## 9. 全片持续生产架构

### 9.1 分层职责

| 对象 | 职责 | 不承担的职责 |
| --- | --- | --- |
| `ProductionRun`（新增） | 一次整部作品运行的范围、预算、汇总、推进与控制 | 不直接提交 ComfyUI，不拥有第二把 GPU 锁 |
| `RunEpisode`（新增） | 本集范围、顺序、计划身份、进度及交付状态 | 不覆盖已有剧本或素材 |
| `RunBatch`（新增） | 将一组已确认生成片段映射到一个现有 ProductionSeries | 不重建另一套 job/attempt |
| `ProductionSeries`（复用） | 当前一批镜头的受管执行、租约、恢复和终结 | 不以单批完成宣告全片完成 |
| Job/Attempt/Artifact（复用） | 逻辑镜头任务、具体尝试及不可变产物 | 不推断用户已接受艺术效果 |
| DeliveryOrder（扩展） | 分集、批次或全片合集的持久装配任务 | 不偷偷删掉缺失片段拼出“完整”成片 |

一个 RunEpisode 可有多个 RunBatch；首版一个 RunBatch 只属于一集，避免批次跨集增加故障耦合。批次数量由连续性、工作单元和资源策略决定，不等于集数。

### 9.2 唯一编排体系

在现有常驻 Worker 主循环中增加短事务的 run 推进一步骤。API 仅落库并返回任务身份；浏览器、HTTP 长连接、`BackgroundTasks` 或内存循环都不是任务权威。

Run 只决定哪些批次应成为可领取状态；实际 series 领取仍走已有机制。保持单机一个 resident Worker 同时领取一个 series 的产品约束，避免两个控制器同时提交同一镜头。

建议一次推进流程：

1. 核对控制请求、版本、预算、生产时间窗口和租约。
2. 合并已持久化的 job、series 和交付结果；不重新调用外部服务来重建已知结果。
3. 识别可运行批次、真实依赖与局部阻塞。
4. 在事务中至多创建规定数量的下一批任务或分集交付订单，使用唯一键防重复。
5. 交由现有执行路径领取；当前推进函数及时返回。
6. 在后续 beat 重复推进，直到本次范围全部交付，或没有可继续的工作且存在待决问题。

### 9.3 首版状态机

`ProductionRun` 建议状态：

| 状态 | 含义与出口 |
| --- | --- |
| `DRAFT` | 尚未满足启动条件；完成校验进入 READY |
| `READY` | 输入完整，可由用户授权启动 |
| `QUEUED` | 已持久化启动，等待调度；资源等待通过 reason/next_check_at 表示 |
| `RUNNING` | 正在推进；允许带 blocker_count 继续独立部分 |
| `PAUSE_REQUESTED` | 不再安排新生成，等待当前已知外部工作到安全边界 |
| `PAUSED` | 安全暂停；带预算、存储、时间窗口或用户原因 |
| `RECONCILING` | 对账所有权或不确定结果；不重放未知请求 |
| `NEEDS_REVIEW` | 尚有必需阻塞，当前没有可继续的独立工作；可核对或显式修订后恢复 |
| `CANCEL_REQUESTED` | 停止新增工作，处理当前外部任务和受管资源 |
| `CANCELLED` | 取消已收尾；保留全部已产出数据 |
| `FAILED` | 不可继续的运行级错误，记录明确原因和已完成范围 |
| `COMPLETED` | 所有必需集与约定交付完成；艺术验收状态另记 |

`COMPLETED` 不用于“所有可运行任务都跑过，但还有必要集缺失”的情况；不以 `COMPLETED_WITH_BLOCKERS` 掩盖缺片。用户决定缩小范围时确认新包/新运行，而不是静默修改旧合同。

### 9.4 依赖、局部失败和跨批次承接

- 区分剧情顺序、媒体续接、生产资源与交付聚合四类关系，避免把所有后集都连成不必要的硬依赖。
- 某一镜头阻塞时，真正依赖其媒体的后件等待；其他独立场次和集可继续。
- 现有 series 的局部失败语义保持诚实；首版可在 series 边界继续其他批次，不要求先重写 series 内全部失败处理。
- 跨 series 的媒体依赖须新增明确的 source job/attempt/artifact 解析与准入检查，不能在批次边界偷偷退回无参考模式。
- 下游 job 只在来源通过、不 stale、版本一致时创建；重拍导致依赖失效时重新计算，旧产物保留。
- 动态硬依赖必须服从已确认包的关系，不允许 Agent 在生产时自创改变剧情的承接。

### 9.5 GPU 与长时间资源治理

- Run 不持有整部作品期限的物理 GPU 租约。
- 当前 series 从首镜启动到末镜完成持有同一 fenced renderer，按现有规则在批次结束时一次释放。
- 下一批重新走受管领取和启动；跨批次热复用作为后续性能优化，必须单独验证所有权转移，不能提前依赖。
- 完成、暂停或取消的资源收尾仍要求 PID/birth 与命名 Job Object 证明。外部进程不接管、不终止；过期时间不证明模型已卸载。
- 长时间生产可监控健康、磁盘、峰值内存和可用显存；模型重启只在无进行中或未知外部任务且所有权可证明时进行。
- 可选 CPU 装配与 GPU 生成并行，受同一资源台账约束；首版默认有界并发，内存或磁盘压力大时串行。

## 10. 持久化数据与一致性设计

### 10.1 优先新增与扩展对象

以下为实现目标，字段最终由迁移与类型合同落实；不是现有 API 已支持的声明。

| 对象 | 核心字段 | 约束 |
| --- | --- | --- |
| `director_package_versions` | project、revision、manifest artifact/hash、scope digest、确认快照与时间、stale | `(project_id, revision)` 唯一；确认后内容不可原地改变 |
| `production_runs` | package id/hash、scope、policy hash、status、state_version、claim owner/expiry、预算与累计量、控制原因、独立 delivery/acceptance 汇总 | 启动幂等键唯一；默认同项目只允许一个活动全片 Run |
| `production_run_episodes` | run、稳定 episode id/order、manifest hash、目标/预计/实际秒数、状态与交付指针 | `(run_id, episode_id)`、`(run_id, order)` 唯一 |
| `production_run_batches` | run/episode、batch key、输入 digest、series id、依赖来源、状态 | `(run_id, batch_key, input_digest)` 唯一；同一 series 不被重复关联 |
| 既有 AgentArtifact/Artifact | 简报、剧本、分集和连续性快照 | 沿用版本、来源、stale、完整性和审计机制 |
| 既有 DeliveryOrder | 新增 scope kind/id/digest，兼容 series/episode/run | 旧 series/version 唯一性保留；新增范围内版本与输入摘要约束 |

DeliveryOrder 扩展时保留旧 `series_id` 数据：旧行 scope 回填为 `series`，新分集订单允许不持有单一 series_id，以有序 EDL 引用多个 series 的真实产物。检查约束确保 scope 与对应外键一致；使用适当的部分唯一索引，不能依赖 SQLite 对 NULL 的唯一性产生错误防重。

### 10.2 四类幂等身份

1. 启动：相同项目、包 hash、范围 digest、政策 hash 和客户端请求键，返回同一运行；新一轮明确生产使用新请求身份。
2. 批次：相同 run、batch key 和输入 digest，最多创建一个 series 关联。
3. 镜头：继续复用现有 job/attempt 幂等与不可变渲染请求；重拍是新尝试或新修订。
4. 交付：相同范围、有效输入产物摘要、剪辑/字幕/声音设置摘要，最多发布一份对应版本的交付结果。

### 10.3 事务与领取

- Run claim、series claim 和资源 lease 分别有明确所有者和 fencing 校验；Run 的推进所有权不能替代 renderer 所有权。
- 写入检查 status、state_version、owner 和相关输入修订；SQLite 使用短事务与有界 busy 重试。
- 不跨 ComfyUI 上传、提交、下载、LLM 调用或 FFmpeg 执行持有 SQLite writer 事务。
- 提交意图、图 hash 在外部调用前提交；外部 ID 返回后立即保存；两者之间崩溃进入对账。
- 上一批完成必须可推导出下一批推进，RunEpisode 就绪必须可推导出交付任务。周期对账扫描填补崩溃窗口，唯一约束保证重复扫描安全。
- 实际产物采用临时文件、完整性校验、原子入库；文件系统与 SQLite 不能假定为一个原子事务，应有孤儿临时文件/已发布文件对账。

## 11. 恢复、异常与自动修复政策

### 11.1 异常处理矩阵

| 异常 | 自动动作 | 禁止动作 |
| --- | --- | --- |
| 浏览器关闭/网络断开 | Worker 继续，重连查询服务端进度 | 依赖前端循环续拍 |
| Worker 失联或机器重启 | 领取恢复资格，核对进程、租约、外部 ID 和已有产物 | 把超时当作任务未提交 |
| 已保存视频、尚未检查 | 验证 artifact/attempt/job/prompt 身份链与磁盘摘要后继续 QC | 为方便而重拍，或先写采用结论再验文件 |
| 明确未提交的连接失败 | 按政策有界重试；保存失败类别和证据 | 将所有超时都归为明确未提交 |
| H3 或 LLM 结果 UNKNOWN | 先核对原任务；能确认结果则采用，无法确认则局部待审 | 用新的请求 ID 隐蔽重放未知请求 |
| 技术解码或文件错误 | 拒绝通过，执行授权范围内的有限修复 | 将 probe 元数据当 decode，或缺工具算 pass |
| advisory VLM/ASR 不可用或失败 | 记录 not_run/needs_review，继续不受影响生产，集中待审 | 卡住生产关键路径，或伪造评审通过 |
| 修复预算耗尽 | 停止该项及硬依赖，推进独立部分 | 无上限重试、删除失败历史 |
| 存储/资源不足 | 在安全边界暂停新提交，展示需要的空间或资源 | 自动删除用户素材、已通过视频或待对账数据 |
| 外部/身份不明的渲染器 | 报告 UNVERIFIED，保留资源对账 | 接管或强杀无法证明归属的进程 |

### 11.2 自动修复授权

导演包启动合同明确允许修改的类型、字段、幅度及次数，例如参数修订、合同内提示词重编译或技术转码。身份、锁定对白、主素材、冻结风格、模型身份与生成模式不可自动替换。

修复必须产生有意义的不同请求修订，记录原因和变化；基础设施重试、模型语义返工、交付重试分别计数。优先保护已通过版本。更换 render binding 必须重新确认包与生产准入。

advisory 模型意见不直接成为无限自动重拍触发器。实际 QC 政策及 final gate 沿用现有产品语义；生产 `PASSED`、交付完成、人工 `accepted` 分别记录。

### 11.3 暂停、预算与取消

- 暂停立即禁止安排新的生成；当前已提交任务默认等待结果安全落盘，暂停页面显示“正在收尾当前片段”。
- 有开始/结束时间窗口时，只在安全边界停止，不用系统时间结束来假定外部任务已结束。
- 预算分别记录生产运行墙钟时间、活跃推理时间、LLM 使用量与修复次数，不能只在前端累加计时。
- 取消不自动删除任何产物，也不释放归属未确认的 renderer lease。
- 用户确认取消当前渲染时，仍须执行受管终止、状态核对和资源收尾；取消请求不等于瞬间完成。
- 不默认关机；完成后可按明确设置停止本项目拥有的后台，API/Worker 的退出顺序需确保最后状态已提交。
- Windows 防睡眠仅在显式启用的活跃生产期生效，结束/暂停时撤销；系统自动重启后须通过既有启动入口恢复 Worker，不能靠“后台一直存在”的假设。

## 12. 逐集后期与全片交付

### 12.1 装配触发与输入

一集所有必需片段通过执行政策、当前有效且输入完整后，创建分集交付订单。输入由冻结剪辑意图和真实产物生成 EDL，明确 job、attempt、artifact、入出点和顺序。

现有 series 自动交付需要协调：归属于全片 Run 的 series 默认只报告批次完成，不将每批都发布为用户最终成片；旧的单 series 入口保持原有行为。用户可查看批次预览，但其标签必须是素材/批次预览。

### 12.2 首版后期范围

- 有序 CUT、经过校验的入出点和输出规格统一。
- 基于已确认文本的字幕稿与时码；实际对白对齐无证据时标待核，不宣称字幕已与声音精确匹配。
- 音量与响度处理、字幕烧录或外挂文件、必要的音画同步检查。
- 可选固定调色预设，必须由已确认的交付合同指定并记录参数，不自动改成其他美术风格。
- 对每集执行探测、实际解码、时长、音轨、字幕及输出完整性检查。

H3 自带对白与声音是默认可用路径；固定音色是增强，不要求每个人物都准备音频主资产。无对白镜头不绑定无关语音参考，保留禁声合同和未用节点剪除。

### 12.3 大规模装配

既有 EditDecisionList 单次合同有 100 项边界。每集超出单次处理范围时，使用有序分页/中间装配段形成分层 manifest，并验证无遗漏/重复；不要简单将上限改成无限大。

FFmpeg 使用文件清单和受控路径，避免 Windows 命令行长度限制。处理必须流式或分块，不把数小时媒体整体读入内存。符合编码参数的输入优先安全拼接；必须转码时记录策略，避免每一层都重复有损编码。

装配任务持久保存 claim、heartbeat 和输入摘要；若使用子进程，记录可核对的进程身份，避免失联后并行启动第二个装配进程。崩溃时核对输出，成功发布采用唯一交付版本和原子文件替换。

### 12.4 全片交付

逐集输出视频、按合同生成的字幕和交付 manifest；全部必需集完成后汇总。合集是可选的独立装配任务，其输入为明确的分集版本，不重新渲染 H3。

必要片段缺失时，不发布“完整一集”。若用户需要缺片预览，必须单独请求并显著标注预览与缺失范围，不能满足正式交付完成条件。

只有最终验收门真实通过，才可显示 accepted。可以自动得到可播放、技术检查通过但 pending_review 的成片；它仍应允许用户回来后集中审阅。

## 13. Web 进度、估算与可观察性

### 13.1 开拍前生产摘要

展示导演包版本、全部/选定集、预计成片时长、生成片段数、模型与工作流、资源预留、自动返工预算、异常政策和预计运行时间。主按钮为“启动整部作品生产”；选择子范围时明确改为“启动所选范围生产”。

### 13.2 运行总览

- 总集数、已交付集、正在生产集、待处理集。
- 当前动作：加载模型/生成/保存/检查/修复/剪辑/等待资源，而不是长期停留在“处理中”。
- 已完成片段/全部必需片段，以及成片覆盖秒数；生成进度与交付进度分别显示。
- 已耗时、最近实际进展时间、最近心跳时间、剩余时间区间与估算依据。心跳存活不等于取得生产进展。
- blocker_count、受影响范围和仍在继续的独立部分。
- 暂停、恢复、取消、打开已交付集、查看问题清单。

时间由服务端持久 UTC 时间戳计算，返回明确时区；前端兼容旧数据缺 Z 的解析问题，不生成负计时。暂停时间、排队时间、推理时间分别统计。

### 13.3 估算与存储

- 按模型、机器指纹、分辨率、时长、参考规模和质量档位分组统计真实耗时，滚动估算并展示置信范围。
- 首次无数据时显示“估算/待校准”，不伪造秒级精确 ETA。
- 估算包括启动、GPU 等待、生成、解码、修复和后期；不能只乘平均 H3 时长。
- 存储估算包含多次尝试、派生帧、临时装配和最终成片；持续检查空间，不把旧数据当成可自动回收空间。
- UI 按集分页查询，使用聚合状态接口或有界事件游标；日志有保留策略，但不自动清理必要审计与产物。
- 默认在项目内显示完成/故障；系统通知由用户启用，不擅自通过邮件或第三方服务发送消息。

## 14. 建议 API 与实现边界

下列路由是拟议接口，开发时需核对现有路由并提交 OpenAPI/合同测试；不能在说明或界面中提前当作已存在：

| 用途 | 拟议接口 |
| --- | --- |
| 创意或原文进入前期任务 | `POST /api/v1/projects/{id}/creative-preparation` |
| 剧本与分集确认 | `POST /api/v1/projects/{id}/script-versions/{version}/confirm`；`.../episode-plans/{version}/confirm` |
| 创建/查询导演包 | `POST/GET /api/v1/projects/{id}/director-packages` |
| 确认与就绪检查 | `POST /api/v1/director-packages/{id}/confirm`；`.../{id}/readiness` |
| 启动及查询全片运行 | `POST/GET /api/v1/projects/{id}/production-runs`；`GET /api/v1/production-runs/{id}` |
| 运行控制 | `POST /api/v1/production-runs/{id}/pause|resume|cancel|reconcile` |
| 分集与问题分页 | `GET /api/v1/production-runs/{id}/episodes|blockers|events` |
| 机器部署推荐 | `POST /api/v1/setup/deployment-recommendations` |

共性约束：写操作沿用 same-origin loopback 与 `x-shine-local-action: 1`、local-user 审计；需要授权的动作继续走 action/snapshot 一次性 grant。请求包含预期修订/hash 和幂等身份，控制操作带 `expected_state_version`；异步动作先持久化，返回 202 和任务身份。

现有素材、安装、workflow profile、style、job、series、delivery API 优先复用。新路由是面向旅程的入口，不能复制绕过门禁的第二套执行实现。

新增目录可按职责使用 `shine/director/` 与 `shine/production/`（最终名称由代码审查确定）；`worker.py` 只保留短小调度入口，避免继续把整套长片逻辑堆入单文件。

## 15. 迁移、兼容与发布

- 使用现有 Alembic 和 SQLite，不新增 Redis/Kafka 或独立任务数据库。
- 迁移新增包与 Run 关系，扩展 DeliveryOrder 范围；保留已有项目、job/attempt、series、产物和审计身份。
- 旧项目默认显示为“尚未生成新版导演包”；提供只读迁移预览，用户选择后生成包草案，绝不自动确认、晋升或开拍。
- 历史通过镜头只有全部 render binding 与完整性匹配时，才可显式选择复用；不把旧通过状态批量回填为新包已通过。
- 旧单 series 制作与交付继续可用；Run 所属 series 使用明确来源字段决定交付归属。
- 新状态字段、范围外键及索引有升级/回退测试；已生产数据回退不得删除产物，必要时采用前向修复和恢复数据库快照。
- 功能开关默认不自动启用全片生产；上线后仍由用户在 Web 中明确启动。
- 涉及 `client_review_identity` 钉住的 worker、preproduction、handoff 或质量客户端变化，旧 VLM revision 按设计失效。正式验收前必须完成真实正负校准、新 revision 发布、旧版弃用、重新分析与冻结计划；缺正式项目环境时记 BLOCKED，不复用旧证据。
- Windows 发布只从最终提交树构建，不夹带模型、数据库、用户素材、视频、密钥或验收证据；保留 cmd ASCII 和含非 ASCII 的 ps1 UTF-8 BOM 要求。

## 16. 分阶段实施计划

不以日历工期代替验收。每阶段为可审查、可回归、可独立收尾的 feature branch/提交；已有未提交工作必须保留，不自动提交、推送或覆盖。

| 阶段 | 主要工作 | 可评审交付 | 退出条件 |
| --- | --- | --- | --- |
| M0 基线与合同 | 梳理现有状态/来源，确定数据和 API、兼容边界，建立有界工作单元 | ADR、合同、迁移设计、范围与依赖案例 | 数据身份与状态转换无歧义，旧流程可保持 |
| M1 双入口与旅程 | 创意/导入统一剧本，分集方案，调整素材与剧本入口、完成判断 | 六阶段 Web、真实持久前期任务、确认差异 | 两条入口都能产出可确认剧本和分集，不丢原文/锁定事实 |
| M2 机器推荐 | 方案兼容矩阵、资源规则、旧模型复用、安装确认和小样反馈 | 推荐页、部署计划、机器实测档案 | 推荐与后端准入一致；未验证组合不标可用 |
| M3 导演包与全片计划 | 复用正式分镜和素材准备，完成包快照/确认、Run/episode/batch 迁移 | 可从 Web 确认包并创建完整 Run | 重复启动幂等，范围覆盖完整，所有旧门禁有效 |
| M4 持续生产与恢复 | Run 推进、跨 series 依赖、局部阻塞、预算/暂停、重启恢复 | 离线全片闭环与故障注入证据 | 无重复提交/重复领取/假完成，独立批次能继续 |
| M5 分集后期与总览 | DeliveryOrder 扩展、跨批次 EDL、逐集字幕/声音/装配和合集、聚合进度 | 多集自动交付与 Web 预览 | 无缺片正式交付，重复装配安全，进度按完整范围计算 |
| M6 真机验收与发行 | 实际部署矩阵、真实 H3 多集、长时间运行、Windows 回归与包构建 | 验收报告、未决清单、最终提交和测试包 | 达到下节真实验收，不把模拟结果当实测 |

M1 与 M2 可分别推进，M3 依赖 M1 的合同，正式开拍依赖 M2 的可执行验证。首版不把所有量化格式、所有显卡或复杂剪辑效果作为 M6 前置；先完成一个明确兼容组合的全片闭环，再扩大矩阵。

## 17. 验收与测试方案

### 17.1 证据等级

报告逐项使用 `DESIGNED / IMPLEMENTED / OFFLINE_VERIFIED / REAL_DEPLOYMENT_VERIFIED / REAL_IMAGE_VERIFIED / REAL_H3_VERIFIED / LONG_RUN_VERIFIED / HUMAN_REVIEW / BLOCKED / NOT_RUN`。每条附精确提交、配置/包 hash、机器指纹、任务/产物身份、命令与结果。

历史短样、Fake、模拟时钟或合同测试不提升到真实长时级别。`HUMAN_REVIEW` 写清通过/待审/拒绝，不能只写“有人看过”。

### 17.2 必须覆盖的确定性和对抗用例

| 类别 | 必须通过的用例 |
| --- | --- |
| 双入口 | 想法生成；导入保留原文；对白/事实改写需确认；缺字段和超长文本不崩溃 |
| 范围覆盖 | 多集数千个逻辑片段分页处理，无遗漏/重复；局部三段或 100 项上限不截掉后文 |
| 资产与风格 | 三种素材方式混合；候选不能自晋升；可选音色不阻塞；冻结后变更使相关包失效 |
| 机器推荐 | 未识别 GPU、多 GPU、资源不足、旧文件复用、编码器占用、过期实测、后端不兼容 |
| 启动与并发 | 双击、请求重发、两个 Worker、Run 重复推进、series 完成到下一批创建之间崩溃 |
| 外部提交 | 提交前失败、提交意图后崩溃、已接收但应答丢失、UNKNOWN LLM/H3 不重放 |
| 产物恢复 | 保存后 QC 前崩溃；磁盘字节被改；身份链错误；采用结论前验证完整性 |
| 依赖 | 同场末帧跨批次续接；独立集继续；重拍失效传播；计划事实不冒充媒体证据 |
| 资源 | series 内同一 renderer、批末一次释放、失联租约保守对账、外部进程不碰、GPU 忙为等待 |
| 控制 | 暂停/取消收尾、预算耗尽、存储不足、重启、时间窗口与系统休眠恢复 |
| 交付 | 一集多 series、超过 100 个 clip 的有界装配、重复任务、FFmpeg 失联、字幕变更只重装配 |
| 完成判定 | 一段通过不算全片完成；缺一必要集不能 COMPLETED；pending_review 不标 accepted |
| Web | 完整双入口至多集交付；刷新/切页保状态；大列表有界；真实预览 URL 可播放 |
| 迁移 | 旧库升级、旧 series 交付兼容、NULL/部分唯一索引、防止双重发布、无历史数据丢失 |

### 17.3 真实验收递进

1. **真实部署小样**：选定硬件组合完成版本/哈希/依赖验证，真实三类生图和 H3 工作流输出；记录资源基线与释放。
2. **真实多集闭环**：至少 3 集，每集约 60 秒、由已确认剧本合理规划；全程从 Web 启动，自动产生多个生产批次和逐集交付，不靠脚本手工驱动下一段。
3. **真实持续生产**：在可承受范围的真实剧本上覆盖至少 8 小时实际活跃生产运行；仍有足够已授权工作以防提前完成。关闭浏览器不影响推进，测量累计资源与产物。
4. **长时稳定性**：独立安排至少 24 小时实际持续运行验收，具备充分任务量。等待/睡眠/暂停不充当活跃生产时长；若未跑满，只按实际时长记录，不能人为慢放或空等补数。
5. **真实恢复演练**：在明确阶段受控终止 Worker；单独验证机器重启恢复。若需要测试应答丢失，先用注入式受控代理/测试环境验证，避免以生产数据试探未知重放。
6. **人工抽查与集中终审**：检查跨集身份、服装、对白、连续性、字幕和剪辑；记录模型局限与返工，不以技术通过代替审美认可。

第 3/4 项生产运行时长与成片时长分开报告；不能把 24 小时运行写成产出 24 小时影片。全片长度依剧本和实际输出计算。首版支持数千任务的规模证据可先离线取得，真实最大规模只能按实跑声明。

## 18. 风险与处理决定

| 风险 | 处理 |
| --- | --- |
| 全片规划耗时与模型输出漂移 | 层级来源、单次有界合同、逐段版本、确定性覆盖检查和用户一次性最终确认 |
| 低配组合不稳定 | 固定兼容矩阵、资源余量、真实小样、标注估算与实测，不推荐未验证能力为默认可用 |
| 数量级增长冲击 SQLite/UI | 短事务、索引、分页 manifest、聚合进度、有界轮询和日志策略 |
| 批次边界丢失连续性 | source job/attempt/artifact 显式跨批次依赖，末帧哈希及媒体 lineage 验证 |
| 一处故障拖停全片 | 仅阻塞真实依赖；运行中展示局部问题，继续独立批次 |
| 无限修复和隐蔽成本 | 分类预算、总预算、安全边界暂停、无意义修订拒绝 |
| 硬盘被长时生产耗尽 | 开拍预估加持续预警、预留装配空间、保留失败/旧版、不自动删用户数据 |
| 后台残留与显存泄漏 | series 级所有权、一次释放、保守对账、运行健康记录 |
| 提示词/工作流版本漂移 | 包与规则固定、运行前校验、变更新版本、不得静默更新 |
| 自动交付被误认为艺术验收 | production/delivery/acceptance 三种状态分开，展示集中待审列表 |
| 引用项目没有可复用源码许可 | 本轮只吸收流程思想；任何源码复用先更新 upstream-audit 并审核 exact revision 和许可证 |

## 19. 完成定义

本轮方案中的“完整建设完成”须同时满足：

1. 两种入口都能形成统一、可确认的剧本和分集计划，原文事实与用户锁定项可追溯。
2. 素材需求逐项支持复用/上传/候选生成，用户明确确认主素材与冻结风格。
3. 有完整范围、版本和授权的内嵌导演包，可直接在 Web 启动整部作品生产。
4. 所有选定集和生成片段进入同一持久运行计划；超过局部三段和单次 100 项后仍覆盖完整。
5. 关闭浏览器后持续生产，异常和重启恢复不造成重复提交、丢产物或失控资源。
6. 独立工作可绕过局部阻塞继续，无法确认的外部结果保持待核，必要内容不被静默跳过。
7. 一集由多个批次组成时仍可自动剪辑交付；可选全片合集不需要重拍。
8. 新机方案推荐、安装与真实小样验证闭环成立，硬件不支持时如实拒绝相应能力。
9. 后端、前端、迁移、Windows 分发和现有产品不变量全部回归，真实多集和长时证据达到声明等级。
10. 最终报告分别列出已实现、离线验证、真实部署/生图/H3/长时验证、人工验收与阻塞项。
